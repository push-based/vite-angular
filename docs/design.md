# vite-plugin-ngp: design

vite-plugin-ngp lets Vite compile Angular one module at a time, using ngp, the Rust-and-TypeScript preprocessor the Angular team merged on 8 October 2026. Vite owns the module graph, hands each `.ts` file to the plugin as the browser asks for it, and gets back ngp's TypeScript with a source map. No whole-program compile happens first.

This page is for whoever builds or reviews the plugin next. It covers why the plugin exists, how it works today, what it doesn't do yet, and where the design is weakest. The evidence behind each choice lives in [ng-hybrid-preprocessor-bench](https://github.com/push-based/ng-hybrid-preprocessor-bench), mainly its [Vite plugin investigation](https://github.com/push-based/ng-hybrid-preprocessor-bench/blob/main/docs/vite-plugin-investigation.md). Individual choices are logged in [decisions.md](decisions.md).

Snapshot: 16 October 2026. ngp built from Angular `92e5aa8` (`22.3.0-next.2`), Vite 8.3.4, Node 26.12.0.

## Why build it

Every Angular dev server today compiles the whole program before it serves a module. `ng serve` runs esbuild and uses Vite only to serve the output. `@analogjs/vite-plugin-angular` compiles the program in `buildStart` and ignores the code Vite passes to `transform`. Both inherit that from ngc, which can't compile a file until it has built a `ts.Program` and analyzed every decorator in it. The bench's audit traced 15 of Analog's workarounds to that one fact: slow cold starts, whole-program recompiles on every edit, styles outside Vite's CSS pipeline, and private Angular APIs that break on minor releases.

ngp removes the constraint. Its Rust analyzer answers per file on demand, and `processFile(file, code)` returns output byte-identical to a full build. The bench measured the first module served in 164 ms on a 5,000-component app, and a one-file edit costing about 1 ms in the analyzer plus 3 ms to regenerate the file.

Nobody else has a Vite plugin on ngp. The Angular CLI plans ngp as a per-file transform inside its esbuild plugin, with Vite still only serving files. `@oxc-angular/vite` is per-file but uses its own compiler and skips template type-checking. The opening closes when Angular ships ngp experimentally, which their blog puts "later this year", or when Analog adopts the CLI's transform mode.

## How it works

The pieces, all in [packages/vite-plugin-ngp/src](../packages/vite-plugin-ngp/src):

**Loading ngp** ([ngp-api.ts](../packages/vite-plugin-ngp/src/ngp-api.ts)). ngp isn't on npm. The plugin imports `preprocessor/api.js` from a toolchain directory that this repo's `pnpm toolchain` builds from Angular's source ([building.md](building.md)). It passes the native engine's path to `createAnalyzer` explicitly, so the loader can't fall back to wasm without anyone noticing. The bench measured wasm at up to twice native's time.

**Compiling a module** ([compiler.ts](../packages/vite-plugin-ngp/src/compiler.ts)). One `HybridCompiler` lives as long as the dev server, in optimize mode. `transform` runs with `enforce: 'pre'` on every `.ts` outside `node_modules`. If Vite's code differs from what the analyzer last saw, the plugin calls `analyzer.updateFileContent` first. Then it calls `processFile(file, code)` and returns the result with a source map. Vite's own TypeScript transform strips the types afterwards. Files ngp leaves unchanged return `null`.

**Handling an edit** ([index.ts](../packages/vite-plugin-ngp/src/index.ts), `hotUpdate`). The plugin sends the new content of a changed `.ts` or `.html` file to the analyzer, which returns every TypeScript file whose output may have changed. The plugin drops those files from ngp's cache, invalidates them in Vite's module graph, and returns them to Vite. It never runs `analyzeOptimizedDelta`, which streams every file in the program again after each edit. Vite asks again for the modules the page still uses, and those get regenerated. An edit to an external template, or a `.ts` edit that only changes a component's inline `template` or `styles`, updates the component in place (next paragraphs). So does an edit to a component stylesheet, which never reaches the analyzer (Component stylesheets, below). Every other edit reloads the page.

**Component HMR** ([index.ts](../packages/vite-plugin-ngp/src/index.ts)). In the dev server, ngp compiles with `enableHmr`, which adds the same initializer to each component that the CLI's compiler emits. At startup, and again whenever an `angular:component-update` event names it, the component imports `<module dir>/@ng/component?c=<id>`. The id is `encodeURIComponent('src/app/home.ts@Home')`. When an external template changes, the plugin asks ngp for that component's update module with `emitHmrUpdateModule`, strips its types with Vite's oxc transform, and stores it. Then it sends `angular:component-update` over Vite's HMR channel. The plugin's middleware answers every `/@ng/component` request, with the stored module or an empty one. Angular's runtime swaps the template into the running component, so state survives: in the playground, a counter at 2 stays at 2 while the heading changes. If the runtime can't apply an update, it sends `angular:invalidate`, and the plugin reloads the page.

**Inline templates and styles** ([hmr-candidates.ts](../packages/vite-plugin-ngp/src/hmr-candidates.ts)). A `.ts` edit takes the same path when it can't have changed anything but a component's look. The plugin keeps the content the analyzer had before the edit, parses both versions with TypeScript, and applies the rules of `analyzeFileUpdates` in `@angular/build`. Every top-level statement must be identical as text. In a component class, the class itself and every decorator field must be identical too, except the values of `template` and `styles`. The plugin then emits update modules only for the components whose values changed, so in a file with three components, editing one template updates one. Anything else, from a new entry in `imports` to a changed selector, input or method, reloads, because an update module can't add dependencies the running module lacks. The comparison is textual and strict: reformatting a method reloads too ([decision 23](decisions.md)). In the playground, editing the rating component's inline template or styles keeps the chosen rating; changing its `imports`, `selector`, an input or a method reloads the page.

Two Vite details shaped this. Vite reloads the page for any changed `.html` file that a hook returns no modules for, because it treats every `.html` file as a page. So for a template edit the plugin returns a module node for the template that Vite has never transformed. Vite stops update propagation at such a node, without reloading. A `.ts` file has no such problem: for an inline edit the plugin returns no modules, which Vite takes as handled. And Vite drops errors thrown from `hotUpdate` silently, so the plugin catches them, logs them, and reloads instead. Vite also handles each changed file on its own, in watcher order. When a template and its component's `.ts` file change in one edit, the template update would run against the old class. So the plugin sends a template update no sooner than 50 ms after the template was written, by its modification time, and only if the class on the page fits it. Counting from the write rather than the watcher's report means the wait is usually over by the time the macOS watcher reports, about 110 ms after the write ([decision 48](decisions.md)). It records when the browser last loaded each `.ts` module and when the watcher last reported a change to it. A change after the last load that wasn't applied in place means the page is reloading for the class, so the template sends nothing and the reload brings it. A change on disk that the watcher hasn't reported yet is waited for, up to a second. Reports that repeat content the plugin already has are ignored: FSEvents on macOS reports some writes twice, and one save's files up to 100 ms apart. Every read of a `.ts` file on this path treats an empty file the way Vite's own read does, as a write still in progress, and waits up to 100 ms for it to land. A save truncates the file and then writes it. Read in between, the plugin would record an empty class, wait a second for a report that never comes, and reload the page a second time ([decision 49](decisions.md)). It waits in the background, after `hotUpdate` has returned: Vite runs the server environment's `hotUpdate` only once the client's is done, and the server has to have the new template before the reload renders the page.

**Adding, renaming and deleting files** ([compiler.ts](../packages/vite-plugin-ngp/src/compiler.ts), `remove`). A new file needs nothing special. The analyzer finds it through the import that adds it, even though its tsconfig lists only the entry points, and the output matches a fresh compiler's whether the import comes in the same save or a later one. A deleted file needs a different call. The analyzer keeps every file the plugin sends it with `updateFileContent` in an in-memory overlay that it never drops, so after a delete it went on compiling importers against the deleted content. For a deleted file the plugin calls `analyzer.invalidateFiles` instead. That drops the overlay, and the analyzer finds the file gone from disk. The plugin also invalidates every importer of the file in Vite's module graph, so each one compiles again: an importer that still uses the file fails, and recovers once the file is back, because Vite retries modules whose imports failed when a file is created. A rename is a delete and a create. The watcher's event type doesn't decide what happened, because on macOS a new file often arrives as an update. The plugin treats a file it can't read as deleted.

Deleting a template exposed a gap in ngp. A component whose `templateUrl` file doesn't exist compiles to an empty template with no diagnostic, even in a fresh compiler, where ngc fails with NG2008. So after compiling a component, the plugin checks that each `templateUrl` file exists, and reports NG2008 itself. And a component whose last compile failed isn't running in the browser, so an in-place update has nothing to update: once its template is back, the plugin reloads the page. [file-changes.test.mjs](../packages/vite-plugin-ngp/test/file-changes.test.mjs) checks all of this: it runs a dev server on a temp app, makes each change on disk, lets Vite's own watcher deliver it, and compares the output with a fresh compiler's.

**Component stylesheets** ([styles.ts](../packages/vite-plugin-ngp/src/styles.ts)). ngp compiles with `externalRuntimeStyles`, which leaves `styleUrl` files out of the component and emits `ɵɵExternalStylesFeature(['/absolute/path.scss'])` instead. A normal-order plugin, `vite-plugin-ngp:styles`, picks that up after Vite's oxc transform, and it handles the stylesheets after `vite:css` has compiled them (Sass, PostCSS, `url()` rewriting) and before `vite:css-post` wraps them in JavaScript, so it only ever sees plain CSS. Scoping is `encapsulateStyle` from `@angular/compiler`, the function the CLI's dev server uses. The plugin never parses Vite's output ([decision 32](decisions.md)).

In the dev server, the plugin replaces each path with a flat name, `card.ngp-<hash of the path>.css`. Angular's runtime adds a `<link>` for it with `?ngcomp=<app id>-c<hash>&e=<encapsulation>`, the CLI's protocol, and the plugin scopes the compiled CSS to that id, or leaves it alone when the id is empty (`None`, `ShadowDom`). The name has no directory because Angular adopts server-rendered `<link>`s by the part of the URL after the last slash. With `/src/app/card.css`, every link was added a second time on hydration, and `ShadowDom` roots got relative links that loaded the wrong URL. The browser resolves the name against the page, so `resolveId` maps it back by name, under any directory ([decision 33](decisions.md)).

A stylesheet edit, or an edit to a Sass partial one uses, sends `angular:stylesheet-update` with the names of the affected component stylesheets. A listener that every component with stylesheets imports in the dev server sets each matching `<link>`'s `href` with a fresh `t=`, in the document and in every shadow root. Vite's own `css-update` can't do it: its client drops the query, `ngcomp` included, and updates only the first matching link ([decision 34](decisions.md)). In the playground, the SCSS meter keeps its level through edits to its stylesheet and to its partial, and the `ShadowDom` box updates in place too.

In `vite build`, client and server, and under Vitest, where jsdom wouldn't load a `<link>`, the plugin replaces each `ɵɵExternalStylesFeature` call with a feature that prepends imported CSS strings (`?inline`) to the component's `styles`. Emulated stylesheets are scoped at build time with a placeholder id, `__ngpcomp__`, that the feature swaps for Angular's `%COMP%`. `%COMP%` itself isn't valid CSS, and Vite's minifier rejects it. The class's encapsulation comes from ngp's metadata. Features run inside `ɵɵdefineComponent` before anything reads `styles`, and `styles` isn't part of the component id, so server and browser agree on ids. Inline `styles` and `<style>` stay with ngp, which compiles them as plain CSS: ngp has no hook to preprocess them.

**Keeping edits cheap** ([entry-tsconfig.ts](../packages/vite-plugin-ngp/src/entry-tsconfig.ts)). After every update, ngp's analyzer reloads its tsconfig and re-expands the `include` globs, walking the whole source tree. That made a one-line edit cost 172 ms at 5,000 components. The plugin writes a tsconfig into Vite's cache directory that extends the user's and lists only the entry points. The analyzer finds every other file by following imports, and the same edit costs about 1 ms. The upstream fix would be to re-resolve entry points only when files are added or deleted. ngp doesn't accept outside contributions, so the workaround stays until Angular fixes it.

**Linking libraries** ([linker.ts](../packages/vite-plugin-ngp/src/linker.ts)). Angular libraries, Angular's own packages included, ship partially compiled: `ɵɵngDeclareComponent(...)` calls that describe a declaration without being its runtime code. Angular's linker rewrites them into the final `ɵɵdefineComponent(...)` code. ngp only compiles the app's own sources, so the plugin runs Angular's Babel linker on any `node_modules` module that contains `ɵɵngDeclare`. It does this in two places: in dev, inside Rolldown's dependency pre-bundling, which runs outside the plugin pipeline, for the client and, with `ssr`, for the server; and in the normal transform for production builds and for dependencies Vite doesn't pre-bundle. `@angular/core` and `@angular/compiler` are skipped, because they define those functions without calling them.

**Compile-time globals** ([index.ts](../packages/vite-plugin-ngp/src/index.ts), `config`). The plugin defines the same globals the Angular CLI does: `ngJitMode` false everywhere, `ngDevMode` false in builds, and `ngServerMode` false in the client environment and true in server environments. Without them, a production build still runs Angular's dev-mode checks.

**Build optimizer** ([optimizer.ts](../packages/vite-plugin-ngp/src/optimizer.ts)). `vite build` runs a copy of the CLI's build optimizer, the pass `ng build` applies to every module, so Rolldown can drop Angular code the app doesn't use. It's unrelated to ngp's optimize mode, which is about how ngp compiles. It runs after the linker for libraries, and after Vite strips types for the app's own modules. A class with `ɵcmp`, `ɵfac`, `ɵprov` and the like moves into an IIFE marked `/*#__PURE__*/`, and so does a TypeScript enum. In `@angular/*` packages that declare `"sideEffects": false`, every top-level call and `new` is marked pure. `forwardRef` is pure through Rolldown's `treeshake.manualPureFunctions`. The pass parses with Vite's own oxc parser and edits with magic-string, so it adds no parser and no Babel. On the playground, the JavaScript on the first page went from 502 kB to 316 kB, against 336 kB from `ng build` of the same app. Decision 24 has the full numbers. The dev server doesn't run it: it would only make each served module slower.

**Type-checking** ([type-check.ts](../packages/vite-plugin-ngp/src/type-check.ts), [type-check-diagnostics.ts](../packages/vite-plugin-ngp/src/type-check-diagnostics.ts)). ngp doesn't type-check. In optimize mode it can generate a type-check block per component file: TypeScript that calls each template expression against the component's types, with a `/*start,end*/` comment after each expression giving its place in the template. The plugin gets those blocks with `getTcbForFile`, from a second `HybridCompiler` on the same analyzer that keeps template whitespace, so spans match ngc's ([decision 30](decisions.md)). It caches them until the analyzer marks a file stale. It writes them into Vite's cache directory, next to a tsconfig that extends the app's, adds them to its `files`, and puts their directory in `rootDirs` so their relative imports resolve to the app's own sources. Then it spawns TypeScript 7's `tsgo` on that tsconfig, in a child process, so neither transforms nor HMR wait for it. An error in an app file is reported where `tsgo` puts it. An error in a block is mapped back with compiler-cli's rule: walk up from the error to the first node with a span comment, and take the file from the block's `ngp-tcb-template-sources` comment. In dev, the first check runs once the server has been idle for 500 ms after it started listening, where idle means no request being answered and no module being compiled (`ServerActivity`, fed by a middleware ahead of Vite's own and by the transform hook; [decision 53](decisions.md)), or 60 s after the start at the latest. Then a check runs 300 ms after the last edit. Errors go to the terminal and to Vite's error overlay, which a small client module opens and closes. `vite build` waits for the check before writing the bundle and fails on any error ([decision 29](decisions.md)). The block's unused-function errors are dropped as ngc drops them, so the app keeps `noUnusedLocals` for its own code ([decision 31](decisions.md)). On the playground a check takes 100–250 ms in dev.

**Build options from `ng build`** ([budgets.ts](../packages/vite-plugin-ngp/src/budgets.ts), [polyfills.ts](../packages/vite-plugin-ngp/src/polyfills.ts)). Three angular.json options have no Vite equivalent, so the plugin takes them, under the CLI's names and in its shapes, so they can be copied over. It doesn't read angular.json ([decision 36](decisions.md)). Every other option maps to Vite config or isn't supported; the site's migration page lists each one.

- `fileReplacements`. Vite alone isn't enough, because ngp's analyzer follows imports on disk: it would read `environment.ts` while Vite bundled `environment.prod.ts`, and a decorator that reads a value from the file would compile against the wrong one. So the replaced file keeps its own module id everywhere. The plugin's `load` hook gives it the replacement's content, and `NgpCompiler.create` sends the same content to the analyzer under the replaced path before anything compiles. Watcher edits to the replacement count as edits to the replaced file. Transforms of a replaced file never update the analyzer: a pre-transform can carry code read just before an edit, and in testing it reverted the analyzer in 2 of 13 runs ([decision 37](decisions.md)). The fixture's banner takes its template from the replaced file, and compiles with the replacement's template ([test](../packages/vite-plugin-ngp/test/build-options.test.mjs)).
- `polyfills`. Each entry module gets them as its first imports, in dev, in the build and on the server ([decision 38](decisions.md)). On the server, `zone.js` becomes `zone.js/node`, and other polyfills are dropped except `@angular/localize/init`, as the CLI does. With `zone.js` listed, a second plugin rewrites `async`/`await` into generators with esbuild and `supported: {'async-await': false}`, the CLI's setting. zone.js can't see a native `await`, so the code after it runs outside Angular's zone and change detection never hears of it. The fixture records the zone that code ran in: `angular` with the rewrite, `<root>` without it, and in a browser the page stays on "loading" without it ([test](../packages/vite-plugin-ngp/test/polyfills.test.mjs), [decision 39](decisions.md)).
- `budgets`. The CLI's calculator and messages, checked in `generateBundle` on the browser build. Initial means the entry chunks, their static imports and the CSS they import. For `anyComponentStyle`, a `styleUrl` file is measured as the CLI measures it: compiled by Vite, minified with esbuild, before scoping. Inline `styles` are measured as written, because ngp ships them that way ([decision 40](decisions.md)).

**Server-side rendering** ([index.ts](../packages/vite-plugin-ngp/src/index.ts), the `ssr` option). The app supplies a server entry, by default `src/main.server.ts`, whose default export is `render(url, document)`. In the [playground](../playground/src/main.server.ts) that's three lines around `renderApplication` from `@angular/platform-server`. The plugin then does four things:

- In dev, a middleware runs after Vite's SPA fallback. For every page request it loads the entry through the `ssr` environment's module runner, passes it `index.html` as Vite transformed it, and returns the rendered page. The browser hydrates that page instead of rendering it again.
- Server environments get their own ngp compiler, compiled without HMR. HMR code imports update modules from URLs only a browser can load, and on the server every component's import failed. Each environment's `hotUpdate` sends edits to its own compiler, so after a template edit the browser updates in place and the next server render shows the edit too.
- Server environments bundle every Angular library (`resolve.noExternal`) rather than letting Node load it: `@angular/*`, plus every dependency that depends or peer-depends on `@angular/core`, which covers Material, NgRx and the like. That makes the linker run on them, and keeps one copy of `@angular/core`. Without it, rendering failed with `NG0203`.
- In dev, the `ssr` environment pre-bundles those libraries, linked, into `node_modules/.vite/deps_ssr`, as the client does into `deps`. Vite turns its optimizer off for server environments, and without it every Angular package was linked and transformed again on each start: the playground's first server-rendered page took 1.3 s on a warm restart, 0.74 s with the cache ([decision 54](decisions.md)). A Rolldown plugin keeps everything the libraries import that isn't an Angular library (rxjs, say) out of the bundle, so Node loads one copy for the bundle and for the app. The server's compile-time globals are baked into the bundle, and its source maps are deleted after Rolldown writes them: reading and combining them cost about 170 ms of the playground's first page, and the pre-bundle is readable as it is.
- `vite build` builds both environments (`builder: {}`): the browser bundle into `dist/client`, and the entry into `dist/server/main.server.js`. Serving them is the app's job. The playground's [server.mjs](../playground/server.mjs) does it with plain `node:http`.

**Internationalization** ([i18n.ts](../packages/vite-plugin-ngp/src/i18n.ts), the `i18n` option). ngp compiles `i18n` attributes exactly as ngc does, into `$localize` tagged templates behind a dead `goog.getMsg` branch, which `ngI18nClosureMode: false` removes. The message ids depend on `enableI18nLegacyMessageIdFormat` and `i18nNormalizeLineEndingsInICUs`, so the compiler passes both through from `angularCompilerOptions`. Everything else is about what `$localize` means at runtime, and the plugin answers it the CLI's way:

- In dev, one locale ([decision 41](decisions.md)). Each entry module first imports a virtual prelude that loads `@angular/localize/init`, the locale's global data from `@angular/common/locales/global`, and its translations, parsed on the server by @angular/localize's own parsers and passed to `loadTranslations`. Template HMR keeps working, because update modules call `$localize` like everything else.
- In `vite build`, every locale from one build ([decision 43](decisions.md)). Vite bundles and minifies once. Then, in a `generateBundle` hook that runs last, the plugin writes each file once per locale below `<outDir>/<subPath>/`. In JavaScript it replaces each `$localize` call with @angular/localize's public `translate()` result, each read of `$localize.locale` with the locale code, and the prelude's placeholder with the locale code plus its locale data. It finds those with Vite's native parser and edits with MagicString, scanning each chunk once for all locales ([decision 44](decisions.md)). Source maps are composed with `@jridgewell/remapping`. `index.html` gets `lang` and a `<base href>` of `<base><subPath>/`, and the build uses `base: './'` so one set of relative URLs serves every locale ([decision 45](decisions.md)). On the playground, two locales cost 2.1 s against 1.8 s without i18n.
- With SSR, the server bundle gets the same treatment, so `dist/server/<locale>/main.server.js` per locale. Each has its locale written in place of `$localize.locale`, so several can run in one Node process. The browser needs `withI18nSupport()` in `provideClientHydration`; without it, Angular hydrated none of the playground's components.
- `ngp-extract-i18n` builds the browser bundle in memory, unminified with source maps and without translating, and runs @angular/localize's `MessageExtractor` over it, as `ng extract-i18n` does over the CLI's output ([decision 42](decisions.md)). Messages from external templates are attributed to the component's `.ts` file and decorator line, because ngp's source map doesn't cover generated template code.

**Testing with Vitest** ([index.ts](../packages/vite-plugin-ngp/src/index.ts), `testing`). When `VITEST` is set, the plugin compiles specs the way it compiles the app, ahead of time with ngp, and changes five things:

- The analyzer starts with no entries. An empty `files` list works: the analyzer reads a file the first time `processFile` asks for it, and follows its imports from there. Compiling every playground module with no entries gives the same output as with all of them in the program ([test](../packages/vite-plugin-ngp/test/entry-tsconfig.test.mjs)), the spec files included. So a run compiles exactly what its specs import. Filtered to the rating spec, ngp sees 4 files and compiles 3, the spec's host component included. The [test](../packages/vite-plugin-ngp/test/vitest.test.mjs) checks this from the plugin's `DEBUG=vite-plugin-ngp` log ([decision 33](decisions.md)).
- `test.server.deps.inline` lists every Angular library, `devDependencies` included, as file-path patterns. Vitest would otherwise hand them to Node unlinked. Only `@angular/compiler` stays unlinked, and it should: `@angular/core/testing` imports it, so TestBed overrides can recompile in JIT.
- A `defineCacheKeyGenerator` callback keeps app modules out of Vitest 5's on-disk module cache. That cache keys a module by its own content, and a compiled component also depends on its template and on the components it imports. Linked libraries stay cached, which halves a warm run: 1.1–1.3 s against 2.1–2.5 s with an empty cache, for the playground's 11 tests on an M2 Max ([decision 34](decisions.md)).
- Vitest sets `server.hmr: false`, so `hotUpdate` never runs. A `server.watcher` listener sends each edit to the analyzer and invalidates the stale modules in every environment. For a template edit it also calls Vitest's public `watcher.onFileChange` with the owning component, because Vitest's own watcher finds no module for an `.html` file and would rerun nothing.
- No HMR code and no SSR. `ngDevMode` stays on, so ngp's `ɵsetClassMetadata` calls run and `TestBed.overrideComponent` works. `supportTestBed` is on by default in `HybridCompiler`, and the plugin leaves it on.

The user writes the setup file: `initTestEnvironment` plus an `afterEach` that resets TestBed. Angular registers that reset itself only when `afterEach` is a global, and Vitest's aren't by default ([decision 28](decisions.md)).

One trap is already fixed. The plugin remembers what the analyzer has seen for each file. For a file it hasn't seen yet, a transform compares against disk. A watcher event can't, because disk already holds the edit. So watcher edits to unseen files, which includes every template's first edit, always go to the analyzer.

A second trap is fixed too. Vite can read a module, the file then changes and the watcher sends the edit, and only then does the module's transform run, with the old code. Sent to the analyzer, that code undid the edit: components compiled before the file's next transform used the old file, and nothing invalidated them later. So the plugin's `load` hook notes when Vite read each `.ts` module, the compiler notes when the watcher last sent each file, and a transform of a module read before that edit leaves the analyzer alone, unless its code is what's on disk now. Vite drops that transform's result, because the edit invalidated the module while it ran, and transforms it again. A [test](../packages/vite-plugin-ngp/test/file-changes.test.mjs) holds a transform between Vite's read and ngp, edits the file, and checks that a component reading a constant from it compiles with the new value. It fails every time without the guard ([decision 46](decisions.md)).

## What works, and what doesn't yet

Verified in the [playground](../playground): `vite build` and `vite preview`, dev-server boot with no console errors and no JIT compiler loaded, signals and control flow, a lazy route, and template and component edits reloading with fresh output.

| Piece | Status |
|---|---|
| Per-module transform, optimize mode | Works |
| Edit → analyzer update → module invalidation | Works. Template, stylesheet and inline style edits update in place, other edits reload |
| Entry-only analyzer tsconfig | Works. Same output as the full tsconfig for every playground module ([test](../packages/vite-plugin-ngp/test/entry-tsconfig.test.mjs)) |
| New, renamed and deleted files | Works. Output matches a fresh compiler, a deleted file that's still used fails until it's back ([test](../packages/vite-plugin-ngp/test/file-changes.test.mjs)) |
| Production build through the same transform | Works, with the CLI's build optimizer. The playground's first page loads 316 kB of JavaScript (99 kB gzipped), and all its JavaScript is 390 kB. `ng build` of the same app gives 336 kB and 383 kB |
| Linker for `node_modules` | Works, in dev pre-bundling and in builds. Babel-based, the same linker the bench's bundles use. The CLI has since moved to an oxc-based linker, which should be faster |

## Where it's weak

- **ngp is a prototype, and the plugin uses it as one.** The plugin types the API by hand and reaches into `HybridCompiler.fileCache`, `analyzer.updateFileContent` and `analyzer.invalidateFiles`, below the public `updateFileContent` that runs the delta. Any Angular commit can break that. Pinning Angular to exactly `22.3.0-next.2` holds it still for now.
- **Nobody can install it.** Using the plugin means building ngp from source with Rust. That's fine for us and a blocker for anyone else, until Angular publishes ngp or we ship prebuilt binaries per platform.
- **File changes are tested on one small app.** The test app has three components. Nobody has added or deleted a file in a large app, deleted a whole directory, or moved files with a tool that writes them seconds apart. Deleting a component that's still used fails with ngp's "'app-greeting' is not a known element", which names the element but not the missing file; Vite's own "Failed to resolve import" would, but ngp runs first. A missing `styleUrl` file isn't checked at all.
- **SSR runs two analyzers.** The browser and server compilers each hold their own ngp analyzer, so a dev server with SSR needs about twice the analyzer memory, and every edit is analyzed twice. One analyzer serving both would need a way to compile with and without HMR from the same state.
- **SSR has no status codes.** `render(url, document)` returns HTML only, so the not-found page answers 200. Angular's way to set the status is `@angular/ssr`'s request and response tokens, which this plugin doesn't wire up.
- **Tests compile the app's code on every run.** Keeping app modules out of Vitest's cache makes the cache safe, and costs 2–20 ms per module per run in the playground. A full run on a large app pays that for every component it imports. Caching them safely would need a key that covers each module's templates, styles and imported components, which the analyzer knows and Vitest's key callback can't ask for synchronously.
- **The type-check is whole-program.** Every check is a full `tsgo` run, helped only by `--incremental` build info. On the playground's 19 components that's 100–250 ms. At 5,000 components, a planted template error took 1.45 s from the edit to the terminal, 300 ms of it the debounce, against 1.66 s for `ng serve` ([bench/](../bench)). So it scales with the app, and at 5,000 components still keeps up with the CLI. Generating every block at startup also runs on Vite's thread, a file at a time: 0.67 s on Super Productivity's 252 components. Since the first check waits for the server to go idle, that no longer delays the first page, but it does delay the first error report: on that app, from 7.1 s to 8.9 s after the start ([decision 53](decisions.md)).
- **The type-check depends on where Vite's cache is.** Its tsconfig lives there, and TypeScript resolves `types` entries like `vite/client` from it. Under the default `node_modules/.vite` that works. A cache directory outside the project breaks the check for apps that list `types`.
- **i18n output is edited after minification.** The translation pass trusts that the minifier leaves `$localize` tagged templates and `$localize.locale` reads recognizable, and that the prelude survives as one statement. That holds for Vite 8.3's oxc minifier on the playground; the minifier already turned the placeholder string into a template literal once, which the pass now accepts. A minifier change could break it with nothing failing at build time, though the [test](../packages/vite-plugin-ngp/test/i18n.test.mjs) checks the German build for untranslated `$localize` calls and missing locale data.
- **A template update waits for the rest of its save.** Measured end to end in [bench/](../bench), a template edit reaches the page in about 120 ms at 1,000 and 5,000 components, the same as `@oxc-angular/vite`, against 1.8 s for `ng serve` at 5,000. Most of that is Vite's watcher on macOS, which reports a write after either about 10 ms or about 110 ms. The plugin's own work is about 5 ms, ngp's update module 3.3 ms of it. But the plugin holds every template update until 50 ms after the template was written, in case the same save changes the component's class ([decision 48](decisions.md)). When the watcher reports fast, that's about 40 ms of waiting, so the fastest edit is about 60 ms against oxc's 16. The 50 ms is a guess at how far apart one save writes its files; nobody has measured it across editors. The wait counts from the file's modification time, so a tool that keeps old times, or a file system that stores whole seconds, gets no wait at all, and a class written right after its template costs a failed update and a reload.
- **Builds are only a third faster than `ng build`.** 20.2 s against 30.1 s at 5,000 components, both type-checking, and 16.7 s without the type-check, a little under Analog's 18.4 s. `@oxc-angular/vite` builds the same app in 1.4 s. ngp's code generation is Angular's template compiler, in TypeScript, and every module goes through it.
- **The cold start pays for the Babel linker.** Cold, the dev server shows the first page of a 5,000-component app in 1.74 s; a restart with Vite's dependency cache takes 0.57 s. `@oxc-angular/vite`'s gap is 0.8 s, so the plugin's dependency pre-bundling is about 0.4 s slower, most likely the linker. Not measured directly. With `ssr`, the server's packages are pre-bundled too, so a cold start links them twice, once per environment.
- **The server's pre-bundle has no source maps.** A stack trace from inside Angular on the server points into `node_modules/.vite/deps_ssr`, not into `fesm2022`. The plugin deletes the maps because Vite parsed and combined them on every start ([decision 54](decisions.md)); the app's own modules keep theirs.
- **Stylesheets take two paths.** Dev serves `<link>`s, builds inline the CSS. The tests run the playground's SCSS component through both, but a bug in one path won't show in the other. The rewrite also finds `ɵɵExternalStylesFeature([...])` in generated code by pattern: that's ngp's and oxc's output, pinned, rather than Vite's, but a change in how either prints the call breaks it.
- **The build optimizer is a copy.** It's the CLI's pass, ported by hand. When the CLI changes its pass, the plugin's copy stays as it is until someone ports the change, and nothing fails to say so. Bundle size is the only signal.
- **The guard against stale transforms needs the plugin's `load` hook to run.** A transform only knows when Vite read its module if that hook saw the load. When another plugin's `load` returns the code first, the time is unknown, and once the watcher has sent an edit to that file, its transforms reach the analyzer only if their code matches disk. Code another plugin makes up for a file on disk would then never reach the analyzer again; the watcher's disk content would. No plugin the tests use does this, apart from file replacements, which have their own rule ([decision 37](decisions.md)).
- **The `ng build` options are copies of the CLI's rules.** The budget calculator, the zone.js detection and the server polyfill list are ported by hand from `@angular/build`. If the CLI changes them, the plugin keeps the old behavior and nothing says so.
- **A replacement's own imports resolve from the replaced file's directory.** The CLI resolves them from the replacement's. For the usual `environment.prod.ts` next to `environment.ts` that's the same directory. A replacement elsewhere with relative imports breaks.
- **Component style budgets depend on plugin order.** The budgets plugin reads each `styleUrl` file between `vite:css` and the styles plugin, which scopes it. If either moves, the measure changes and nothing fails. Inline `styles` are measured as written, larger than `ng build` measures them, because ngp ships them unminified.
- **The async rewrite parses every chunk again.** esbuild re-reads each output chunk that contains `async`, which cost about 60 ms per build on a 311 kB bundle, and in dev it runs on every served module that contains `async`. It scales with bundle size, and nobody has measured a large app.

## What's been measured, and what's next

[bench/](../bench) measures the plugin against `ng serve`/`ng build`, Analog's default path and `@oxc-angular/vite` on the bench's generated apps (100, 1,000 and 5,000 components) and the playground, end to end in headless Chrome. The results are on the docs site's [Performance page](../site/content/performance.md). In short, at 5,000 components, measured on 17 October 2026: first page 1.74 s cold against `ng serve`'s 28.3 s, a template edit in about 120 ms against 1.8 s, a build in 20.2 s against 30.1 s, a dev server holding 1.0 GB after a restart against `ng serve`'s 6.0 GB, and output within 3% of `ng build`'s. `@oxc-angular/vite` is faster at all of them but the typical template edit, where they tie, without type-checking or `@defer` code-splitting.

The bench also runs two real open-source apps, Super Productivity (Angular CLI) and Ghostfolio (Nx), against the CLI each is built with, with memory recorded next to time, on GitHub's Ubuntu runners as well as on a laptop ([Benchmarks page](../site/content/benchmarks.md), [decision 50](decisions.md#50-benchmark-two-real-apps-against-their-own-cli-on-githubs-runners)). What those two apps needed to run on a per-file compiler at all is written up there and in [bench/README.md](../bench/README.md). Both pages carry figures drawn from the result files by `bench/charts.mjs`, inline SVGs on the site's tokens ([decision 51](decisions.md#51-draw-the-benchmark-figures-as-inline-svg-from-the-sites-tokens)), above the tables they summarize.

Not measured yet: how far apart editors write one save's files, which decides the template update's wait; a library-heavy enterprise app; and Windows.
